# ESAF-1700 Enterprise AI Data Model

**Status:** Working Draft
**Version:** 0.1.0

## Purpose

ESAF-1700 defines the canonical entities, attributes, relationships, and identifier conventions used to describe enterprise AI capabilities, systems, assets, ownership, risk, lifecycle decisions, exceptions, and assessment records across the ESAF library. It gives every companion publication a shared vocabulary so that inventory records, control evidence, crosswalk mappings, and profile instances can be linked and reconciled without duplicating meaning.

## Scope and nonclaims

ESAF-1700 is a canonical conceptual and logical data model. It is not a runtime database schema, API contract, product data model, or vendor implementation mandate. An organization's inventory system, governance, risk, and compliance platform, or model registry is not required to store these entities using these exact tables, fields, or storage technology. Conformance with ESAF-1700 means an organization's records can be reconciled to this shared meaning when exchanged or assessed, not that its internal schema matches field-for-field.

ESAF-1700 does not itself establish certification, compliance, or conformance with any external framework. It does not create new control requirements, assessment procedures, or maturity criteria; those remain the authority of ESAF-1100 and [ESAF-1500](../assessment/ESAF-1500.md). Recording data that conforms to this model does not by itself demonstrate control effectiveness, evidence sufficiency, or risk acceptance.

## Relationship to the ESAF library

[ESAF-1000](../framework/ESAF-1000.md) establishes the inventory, accountability, risk-classification, and lifecycle-gate concepts that ESAF-1700 formalizes as entities (Section 8, Section 6.4, and Section 9.3). [ESAF-1500](../assessment/ESAF-1500.md) is authoritative for evidence, assessment-result, finding, and maturity semantics. ESAF-1700 reuses the ESAF-1500 field contracts and identifier patterns unchanged rather than defining parallel structures, so that an evidence record or assessment result remains a single record regardless of which publication references it.

## Design principles

- **Single authoritative meaning.** Each entity has one canonical definition, reused rather than restated by companion publications.
- **Traceability by reference.** Entities are linked through stable identifiers rather than copied attributes, so a record can be updated once and referenced consistently.
- **Risk-proportionate exchange.** The model shall not require an organization to expose more detail than an exchange purpose and its authorization justify.
- **Reuse before invention.** Where ESAF-1500 already defines a record contract, ESAF-1700 reuses it exactly rather than approximating it.

## Core entities

| Entity | Canonical source | Purpose |
|---|---|---|
| AI Capability | ESAF-1000 Section 3.1, 8.2 | Business or operational function that uses AI to produce or materially influence an outcome. |
| AI System | ESAF-1000 Section 3.2 | Models, data, software, infrastructure, identities, integrations, workflows, people, and processes delivering a capability. |
| AI Asset | ESAF-1000 Section 3.3 | Identifiable component supporting an AI system, including a model, dataset, prompt, embedding, vector store, agent, tool, API, or runtime environment. |
| Accountable Owner | ESAF-1000 Section 3.4 | Individual with authority and responsibility for a capability's purpose, outcomes, risk, resources, and lifecycle decisions. |
| Risk Classification | ESAF-1000 Section 6.4 | Documented risk determination governing a capability's required gates, controls, evidence, and review frequency. |
| Lifecycle Gate Decision | ESAF-1000 Section 9.3 | Recorded authorization, condition, or rejection at a lifecycle gate. |
| Exception | ESAF-1000 Section 12.10 | Time-bounded, approved deviation from an applicable requirement with compensating measures. |
| Evidence Record | ESAF-1500 | Attributable, quality-evaluated artifact supporting an assessed fact or condition. |
| Assessment Result | ESAF-1500 | Scoped determination of design and operating effectiveness supported by evidence. |
| Finding | ESAF-1500 | Nested observation within an assessment result with severity, ownership, and disposition. |

## Entity contracts

### AI Capability

| Attribute | Description |
|---|---|
| `capability_id` | Stable identifier, recommended pattern `^CAP-[A-Z0-9][A-Z0-9-]*$`. |
| `name`, `description` | Human-readable identification. |
| `approved_purpose` | Approved use and intended outcome. |
| `business_owner_ref`, `technical_owner_ref` | References to Accountable Owner records. |
| `organizational_unit`, `users`, `affected_parties` | Deployment context and impacted populations. |
| `deployment_status` | Current lifecycle stage from ESAF-1000 Section 9.2. |
| `criticality`, `risk_classification_ref` | Reference to the current Risk Classification record. |
| `system_refs` | One or more AI System records that deliver the capability. |
| `applicable_obligations`, `profile_refs` | Applicable legal, regulatory, or ESAF-1800 profile references. |
| `review_date`, `retirement_authority` | Governance dates and accountable retirement decision-maker. |

An AI Capability shall have exactly one current Risk Classification and current business and technical Accountable Owners at all times. Superseded classifications and owners shall be retained as history rather than deleted.

### AI System

| Attribute | Description |
|---|---|
| `system_id` | Stable identifier, recommended pattern `^SYS-[A-Z0-9][A-Z0-9-]*$`. |
| `capability_refs` | One or more AI Capability records the system delivers. |
| `asset_refs` | Constituent AI Asset records, forming the system's AI Bill of Materials. |
| `provider`, `hosting`, `architecture_pattern_ref` | Provenance, hosting model, and reference architecture pattern. |
| `data_categories`, `jurisdictions` | Data classifications, sources, and residency. |
| `external_integrations` | Material dependencies, agents, tools, and APIs. |
| `technical_owner_ref` | Reference to the accountable technical or service owner. |

A system may deliver more than one capability; a capability may depend on more than one system when composed of separable services. Each dependency shall be recorded explicitly rather than inferred.

### AI Asset

| Attribute | Description |
|---|---|
| `asset_id` | Stable identifier, recommended pattern `^AST-[A-Z0-9][A-Z0-9-]*$`. |
| `asset_type` | Model, dataset, prompt, embedding, vector store, agent, tool, API, knowledge source, or runtime environment. |
| `system_refs` | AI System records that use the asset. |
| `provenance`, `version`, `license` | Origin, version, and licensing terms. |
| `integrity_ref` | Digest or verification method establishing artifact integrity. |
| `retirement_status` | Active, deprecated, or retired state. |

An asset may be shared across multiple systems. Shared-asset changes shall be propagated to every dependent system record rather than tracked separately per system.

### Accountable Owner

| Attribute | Description |
|---|---|
| `name`, `role`, `organization` | Reuses the ESAF-1500 `person` contract fields unchanged. |
| `accountability_scope` | The capability, system, or asset the owner is accountable for. |
| `owner_type` | Business owner, technical or service owner, data owner, or another ESAF-1000 Appendix C role. |
| `effective_from`, `superseded_by` | Tenure boundaries supporting historical traceability. |

An Accountable Owner record is a role assignment, not solely a person directory entry; a person may hold multiple concurrent Accountable Owner records across different capabilities.

### Risk Classification

| Attribute | Description |
|---|---|
| `classification_id` | Stable identifier, recommended pattern `^RSK-[A-Z0-9][A-Z0-9-]*$`. |
| `capability_ref` | The classified AI Capability. |
| `tier` or `level` | Organization-defined risk tier consistent with ESAF-1000 Appendix B. |
| `criteria_refs` | Documented criteria applied, consistent with ESAF-1000 Section 6.2. |
| `determined_by`, `determined_at` | Accountable decision-maker and determination date. |
| `required_gates`, `required_controls` | Gates and controls the classification triggers. |
| `review_date` | Next scheduled or triggered reassessment. |

A capability's current classification shall be unambiguous; superseding a classification shall create a new record rather than mutate the prior one.

### Lifecycle Gate Decision

| Attribute | Description |
|---|---|
| `gate_decision_id` | Stable identifier, recommended pattern `^GATE-[A-Z0-9][A-Z0-9-]*$`. |
| `capability_ref` | The reviewed AI Capability and reviewed version. |
| `gate` | The ESAF-1000 Section 9.3 gate being decided. |
| `decision` | Approval, rejection, or conditional approval. |
| `conditions`, `accepted_residual_risk` | Recorded conditions and accepted residual risk with expiration. |
| `reviewers`, `decision_authority` | Required reviewers and the accountable decision authority. |
| `evidence_refs` | Evidence Record identifiers evaluated for the decision. |
| `next_review_or_trigger` | Next scheduled review date or triggering event. |

### Exception

| Attribute | Description |
|---|---|
| `exception_id` | Stable identifier, recommended pattern `^EXC-[A-Z0-9][A-Z0-9-]*$`. |
| `requirement_ref` | The specific requirement or control the exception departs from. |
| `scope_ref` | The affected AI Capability, AI System, or AI Asset. |
| `justification`, `risk` | Rationale and identified risk from the deviation. |
| `compensating_measures` | Measures offsetting the unmet requirement. |
| `owner`, `approver` | Accountable requesting owner and approving authority. |
| `expiration`, `remediation_plan` | Time-bound expiry and planned remediation. |

An Exception shall not be represented as satisfying the requirement it departs from; it records a governed, time-bounded risk acceptance.

### Evidence Record

Evidence Record reuses the ESAF-1500 evidence-record contract exactly, including the `^EVD-[A-Z0-9][A-Z0-9-]*$` identifier pattern, the seven quality attributes, and the `traceability` object linking to requirement, procedure, and result identifiers. Within ESAF-1700, an Evidence Record's `scope.description` may additionally identify the AI Capability, AI System, or AI Asset it concerns; this data-model usage does not alter the ESAF-1500 contract.

### Assessment Result

Assessment Result reuses the ESAF-1500 assessment-result contract exactly, including the `^ASR-[A-Z0-9][A-Z0-9-]*$` identifier pattern, the `Examine`, `Interview`, `Test`, and `Observe` methods, and the `satisfied`, `partially_satisfied`, `not_satisfied`, `not_applicable`, and `not_assessed` determination vocabulary. Within ESAF-1700, an Assessment Result's `assessment_scope.subject` may identify an AI Capability, AI System, or AI Asset record by identifier.

### Finding

Finding reuses the ESAF-1500 finding contract exactly, including the `^FND-[A-Z0-9][A-Z0-9-]*$` identifier pattern, `critical`, `important`, and `minor` severity, and the `open`, `resolved`, and `accepted` disposition states. A Finding is always nested within an Assessment Result and is not an independently exchanged top-level record.

## Relationship model

- An Accountable Owner is accountable for one or more AI Capability records; each capability has at least one current business and technical owner.
- An AI Capability is delivered by one or more AI System records; an AI System may deliver more than one capability.
- An AI System is composed of one or more AI Asset records; an AI Asset may be shared across multiple systems.
- An AI Capability has exactly one current Risk Classification and a retained history of superseded classifications.
- An AI Capability accumulates Lifecycle Gate Decision records over time, one per gate instance, consistent with ESAF-1000 Section 9.3.
- An Exception references the specific requirement it departs from and the AI Capability, AI System, or AI Asset it applies to; it does not modify the referenced requirement.
- An Evidence Record's `traceability` links to the requirement, procedure, and Assessment Result identifiers it supports; an Assessment Result's `evidence_refs` links back to the Evidence Records it relies on.
- A Finding is nested in exactly one Assessment Result and references the Evidence Records supporting the observed condition.

## Exchange guidance

When exchanging records between organizations, tools, or ESAF publications:

- Evidence, assessment-result, and finding records shall use the ESAF-1500 identifier patterns, field names, and vocabulary unchanged. A receiving system shall not rename or reinterpret `EVD-`, `ASR-`, or `FND-` fields.
- Cross-entity references shall use the referenced entity's stable identifier rather than an embedded copy of its attributes, so that later updates remain discoverable at the source record.
- An exchange shall state the scope, period, and purpose for which records are shared, consistent with the ESAF-1500 evidence `scope` and `period` contracts, so a recipient does not infer broader applicability than was authorized.
- Maturity claims exchanged alongside these entities shall use the ESAF-1500 `M0` through `M4` scale and criteria unchanged; a data exchange shall not introduce a profile-local maturity scale.
- An exchange that cannot supply a required attribute shall omit the record rather than populate it with placeholder or inferred values.

## Nonclaims

ESAF-1700 does not certify, attest, or imply compliance for any capability, system, asset, or organization. Populating these entities does not constitute an ESAF-1000 conformance claim, an ESAF-1500 assessment result, or equivalence with an external framework. This document does not mandate a specific database technology, storage format, or product schema; it defines shared meaning for records that organizations and tools may represent in whatever technical form is fit for purpose.
